ABSTRACT

The "Bus Ticket Booking System" is a comprehensive software application developed to automate the process of querying, booking, and managing bus travel tickets. This project aims to digitize traditional manual ticketing systems, thereby increasing efficiency, reducing human errors, and providing a seamless consumer experience. Using modern programming constructs in Java, interactive UI built with Swing, and efficient data handling via JDBC interfacing with Oracle Database, this project delivers a robust, scalable, and secure application.

Key features include user registration, searching for buses based on diverse routes, real-time seat availability checking, booking confirmation, and basic administrative capabilities for managing schedules. The resultant application demonstrates a practical manifestation of object-oriented concepts, relational database management, and user interface design suitable for commercial adoption in the transport industry.

1. INTRODUCTION

1.1 Brief Information about the Project

The Bus Ticket Booking System is an intelligent application constructed to help bus service administrators and prospective travelers alike. The primary capability of this application is enabling customers to examine bus schedules, discover available seats, and effortlessly secure legitimate bookings without physically visiting a reservation counter. Admins securely log in to observe operations, manage bus listings, and analyze routes efficiently.

1.2 Motivation and Contribution of Project

The core motivation for proposing this project derives from the persistent inadequacies noted in manual ledger-based transportation booking paradigms. Queues, data loss, delayed processing, and double-booking incidents are profound issues. This project contributes a centralized, computerized environment that synchronizes booking state in real time. It minimizes manual input overhead, bolsters passenger convenience, and ultimately improves the operational efficiency of the transport entity.

1.3 Objectives of the Project

The primary objectives formulated for this project are as follows:

  • To construct an intuitive and user-friendly GUI facilitating straightforward navigation.
  • To engineer a robust back-end database layout to securely hold passenger, route, and transaction data.
  • To devise dependable booking algorithms that eliminate occurrences of seat overlapping.
  • To streamline the ticket generation and cancellation process.

1.4 Scope of the Project

The scope encompasses the end-to-end management of reservations within a constrained bus network environment. It covers modules including User Management, Route and Bus Configuration, Ticket Reserving, and Seat Mapping. Future iterations outside the current scope might embrace payment gateway assimilation and GPS-based live tracking, but the current build tightly focuses on foundational scheduling and transactional stability.

2. SYSTEM ANALYSIS

2.1 Functional Requirements

Functional requirements detail the specific behaviors and functions the system must support:

  • User Authentication: Secure login mapping to user or admin roles.
  • Search Routing: Filtering scheduled buses by source, destination, and exact dates.
  • Seat Selection: Real-time GUI picking of specific open seats on a bus.
  • Reservation & Cancellation: Capability to formally lock a booking into the database, and conversely relapsing it.

2.2 Non-Functional Requirements

These characterize system performance and architectural attributes:

  • Reliability: System accurately calculates and maintains data consistency across multiple transactions.
  • Usability: Provided GUI is straightforward, necessitating negligible learning curves.
  • Performance: Data querying happens instantaneously without observable lag.

4. DATABASE DESIGN

4.1 Database Tables

The entity-relationship structure revolves thoroughly around principal entities essential for transportation logistics. The main tables generated are: Users, Buses, Routes, and Bookings.

4.2 Table Structure

Listed below are the schemas formulated for primary data collection:

  • USERS_TBL: USER_ID, FULL_NAME, EMAIL, PASSWORD, ROLE_TYPE, PHONE
  • BUSES_TBL: BUS_ID, REGISTRATION_NO, TOTAL_SEATS, OPERATOR_NAME
  • ROUTES_TBL: ROUTE_ID, BUS_ID, SOURCE_CITY, DEST_CITY, DEPARTURE_TIME, ARRIVAL_TIME, FARE
  • BOOKINGS_TBL: BOOKING_ID, USER_ID, ROUTE_ID, SEAT_NUMBER, BOOKING_STATUS, BOOKING_DATE

4.3 Keys and Constraints

All tables strictly apply foundational RDBMS integrity paradigms:

  • Primary Keys: Applied to identify rows uniquely (e.g., USER_ID, BOOKING_ID).
  • Foreign Keys: Enforced relationally linking dependencies (e.g., BOOKINGS_TBL relies explicitly on existing USER_ID and ROUTE_ID).
  • Not Null & Unique: Assuring data completeness and preventing duplicate identical registrations on critical columns like EMAIL.

4.4 Table Relationships

A "One-to-Many" relationship governs most associations. A singular User may commit multiple Bookings. Concurrently, a singular Route accommodates multiple concurrent Bookings up to the bus's capacity threshold. These structural interlockings assure normalization parameters are rigorously met.

5. SYSTEM DESIGN

5.1 System Architecture

The system embodies a typical monolithic two-tier layout suitable for localized desktop deployment. Tier 1 encompasses the Presentation and Business Logic stratum—encapsulated wholly within Java runtimes operating the Swing application logic. Tier 2 strictly pertains to the Oracle Database backend operating locally or adjacently on a network, handling SQL-based persistence logic directly channeled via the JDBC driver bridge.

5.2 Modules Description

  • Authentication Module: Grants conditional access comparing inserted credentials against secured cryptographic hashes within the database.
  • Catalog Interface Module: The mechanism querying the routing database to exhibit schedule structures sorted logically by proximity or date.
  • Transaction Module: The transactional engine guaranteeing that seat deductions apply atomically, avoiding database corruption if power or connection fails intermittently.

6. SYSTEM IMPLEMENTATION

Implementation transitioned the theoretical designs into observable executable programs. The backend Oracle schemas were engineered first. Post-database modeling, DAO (Data Access Object) classes were structurally coded to abstract away complex raw SQL mechanics from the GUI. The frontend progressively expanded using JFrame layers, implementing ActionListeners dictating reactive logic loops upon user inputs.

Quality assurance methods involved extensive iterative testing. Black-box unit tests verified login rejections, bounded seat limitations, and SQL injection protections actively validating the sturdiness of the delivered binaries.

7. CONCLUSION

The development and execution of the "Bus Ticket Booking System" have successfully demonstrated the theoretical implementation of software engineering philosophies. The project adeptly bridges user-friendly interactive elements through Java Swing with robust data containment using Oracle Database schemas. It definitively achieves the primary objective of mitigating the flaws inherent in manual legacy booking methodologies, yielding an efficient, accurate programmatic solution applicable immediately to real-world deployment parameters.
